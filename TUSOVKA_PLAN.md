# Тусовка. План реалізації

Перша редакція, 24 листопада 2026 року. Джерело вимог — «Тусовка». Завдання та правила оцінювання, сторінки 1–3. Локальна копія — `Тусовка_завдання_та_оцінювання.pdf`. Цей файл фіксує робочі рішення та результати перевірок.

## 1. Що має працювати

| Вимога PDF | Де її перевірити |
| --- | --- |
| Реєстрація, вхід за email і паролем, вихід | Створити акаунт, вийти й увійти знову. |
| Створення події | Зберегти назву, опис, дату й час, місткість, обкладинку та видимість. |
| Головна сторінка | Побачити майбутні публічні події. Знайти потрібну за частиною назви. |
| Сторінка події | Записатися, скасувати участь, побачити залишок місць, додати коментар. |
| Керування подією | Автор може її редагувати й видаляти, а також бачити список учасників. |
| Приватні події | Користувач відкриває запрошення й отримує доступ до однієї події. |
| Мій профіль | Увійти у свій профіль і побачити створені події та записи на події. |

Для здачі потрібні репозиторій GitHub або GitLab із доступом на читання та README з командами запуску і потрібними змінними середовища. Деплой бажаний, промпти для ШІ можна додати за бажанням. Якщо застосунок не запускається за README, його не можна оцінити.

Розробка триває 20–30 хвилин. Далі йде загальне рев’ю без розкриття конкретних багів, час на допрацювання та фінальна перевірка. У першому рев’ю найсерйозніша проблема визначає оцінку «добре / середньо / погано» окремо для безпеки, надійності й якості. У фіналі ці категорії дають максимум 40, 30 і 30 балів відповідно. Критична, серйозна й незначна проблеми коштують 10, 5 і 2 бали відповідно. Мінімум для кожної категорії — 0. Бонуси: до +5 за автотести однією командою з негативними сценаріями, до +5 за дизайн і UX, +3 за робочий деплой.

## 2. Архітектура та структура репозиторію

Django 5.2, серверні HTML-шаблони, один файл стилів, SQLite і Pillow для обкладинок. HTML-форми працюють із сесіями Django. Усі дані, включно з підготовленими обкладинками, зберігаються у SQLite. Для локального запуску достатньо Python і залежностей проєкту. Окремий фронтенд або зовнішнє сховище для першої версії не потрібні.

```text
manage.py
requirements.txt
README.md
.env.example
.gitignore
config/
  settings.py, urls.py, wsgi.py
accounts/
  models.py, forms.py, views.py, urls.py, migrations/
events/
  models.py, forms.py, views.py, urls.py, migrations/
  access.py, services.py, tests.py
templates/
  base.html, accounts/, events/
static/
  styles.css
```

`accounts` відповідає за користувачів і вхід. `events` відповідає за події, запрошення, участь, коментарі й дані для профілю. `events/access.py` визначає доступ до події та керування. `events/services.py` виконує операції, де права й дані потрібно перевірити в одній транзакції. Представлення зв’язують форми, правила доступу та шаблони. Модель користувача й `AUTH_USER_MODEL` фіксуємо перед першими міграціями.

## 3. Дані та правила

| Модель | Поля та обмеження |
| --- | --- |
| `User` | Email — ідентифікатор входу. При реєстрації та вході однаково прибираємо пробіли по краях і приводимо email до нижнього регістру. База гарантує унікальність збереженого email. Пароль обробляють засоби Django. Необов’язкове ім’я для показу, запасний підпис «Учасник №…». |
| `Event` | Автор, назва, пошуковий ключ назви, опис, час початку, місткість, публічна або приватна видимість, хеш чинного токена запрошення (лише для приватної), дата створення. Власника призначає сервер. База гарантує додатну місткість. |
| `EventCover` | Один запис на подію. Зберігає байти підготовленого JPEG і видаляється разом із подією. Повертається лише через маршрут із перевіркою доступу. |
| `Participation` | Подія, користувач, час запису. Унікальність пари «подія + користувач» у базі. Один запис займає одне місце. |
| `Comment` | Подія, автор, текст, час створення. Коментар є звичайним текстом, який шаблон екранує. |
| `EventAccess` | Подія, користувач. Унікальність пари «подія + користувач». Запис означає, що акаунт прийняв чинне запрошення в межах поточного приватного періоду події. |

Пропоновані межі для першої версії: назва 1–120 символів, опис 1–3000, місткість 1–1000, коментар 1–1000 після прибирання зовнішніх пробілів. Пароль передається валідаторам без обрізання. Назву зберігаємо для показу окремо від нормалізованого пошукового ключа. Для ключа й запиту застосовуємо однакову Unicode-нормалізацію та `casefold()`, щоб «КИЇВ» знаходив «Київ» у SQLite. Ключ оновлюється разом із назвою.

Форма приймає місцевий час `Europe/Kyiv` і показує цей пояс поряд із полем. Зберігаємо час у UTC, порівнюємо з поточним часом сервера. Нова подія має починатися в майбутньому. Для минулої події автор може виправити опис або інші поля, залишивши час як є, або перенести її в майбутнє. Якщо час двозначний або не існує через переведення годинника, форма просить вибрати інший. Для Windows передбачаємо залежність `tzdata`.

Обкладинка обов’язкова при створенні. Під час редагування порожнє поле лишає попередню картинку. Приймаємо JPEG, PNG або WebP до 3 МБ і до 12 мегапікселів. Визначаємо формат декодуванням, обмежуємо розміри перед повним завантаженням пікселів і зберігаємо заново як JPEG зі стороною до 1600 пікселів. Непридатний файл дає помилку форми. Картинку обробляємо до відкриття транзакції, а її підготовлені байти зберігаємо разом зі зміною події. Це дозволяє відкотити і поля, і обкладинку при невдалому збереженні.

## 4. Екрани, маршрути та поведінка

| Екран або дія | Маршрут і метод | Поведінка |
| --- | --- | --- |
| Каталог | `GET /?q=…` | Лише публічні події, у яких початок строго в майбутньому. Пошук за частиною назви. Сортування за початком і ID. Картка має обкладинку, назву, час і залишок місць. |
| Акаунт | `GET/POST /register/`, `GET/POST /login/`, `POST /logout/` | Реєстрація входить у новий акаунт. Після входу повертаємо на перевірену локальну сторінку. Хибні дані входу дають спільне повідомлення для невірного email і пароля. Вихід очищує сесію. |
| Створення | `GET/POST /events/new/` | Доступно після входу. Після створення відкривається сторінка події. Автор може створити запрошення для приватної події. |
| Подія | `GET /events/<id>/` | Назва, обкладинка, дата й час, опис, вільні місця, статус участі та коментарі. Автору також показуємо керування і посилання на список учасників. |
| Обкладинка | `GET /events/<id>/cover/` | Перевірка доступу до події. Видаємо JPEG з фіксованим типом і `Cache-Control: private, no-store`, щоб браузер не використовував попередній публічний кеш після зміни видимості. |
| Участь | `POST /events/<id>/join/`, `POST /events/<id>/cancel/` | Запис потребує доступу та вільного місця. Скасування видаляє тільки власний запис. Після успіху оновлюємо сторінку через перенаправлення. |
| Коментар | `POST /events/<id>/comments/` | Додати коментар може авторизований користувач із доступом. Читати їх може кожен, кому доступна сторінка. Коментарі залишаються доступними після початку події. |
| Керування | `GET/POST /events/<id>/edit/`, `GET/POST /events/<id>/delete/`, `GET /events/<id>/participants/` | Тільки для автора. Видалення має екран підтвердження та виконується POST. У списку учасників показуємо імена чи запасні підписи. |
| Запрошення | `GET/POST /invite/<token>/`, `GET/POST /invite/continue/`, `POST /events/<id>/invite/` | Сторінка запрошення пропонує прийняти його. Для гостя спочатку вхід або реєстрація. Автору доступна генерація нового посилання, яка робить попереднє посилання недійсним. |
| Мій профіль | `GET /me/` | Тільки власний профіль. Секції «Я створив» і «Я йду» показують також минулі події з відповідною позначкою. Записи сортуємо за часом участі, щоб приховані дати подій не визначали порядок карток. Елементи з відкликаним доступом показуються без подробиць. |

Навігація: каталог, створення події, профіль, вхід або вихід. Основні стани: ще немає подій, пошук порожній, місця закінчилися, подія почалася, помилка форми, запрошення недоступне. Форма із помилкою зберігає введений текст і повідомляє, якщо картинку потрібно вибрати заново. Інтерфейс українською, з видимим фокусом і підписами полів, на телефоні картки йдуть в одну колонку. Списки подій, учасників і коментарів мають порційне завантаження. Стан після успішної дії показуємо коротким повідомленням Django.

## 5. Доступ і життєвий цикл запрошення

- **Публічна подія.** Гість може відкрити сторінку й обкладинку, зокрема після початку за прямим посиланням. Для запису або коментаря потрібен вхід. Авторство завжди перевіряє сервер.
- **Приватна подія.** Доступ має автор або акаунт із відповідним `EventAccess`. Сам запис на подію не надає доступу. Перевірка однакова для сторінки, обкладинки, коментарів, запису й посилань із профілю. Акаунт без доступу отримує 404. Для доступної події авторизований користувач без права керування отримує 403. Особисті сторінки, сторінку події та приватні відповіді не кешуємо.
- **Прийняття запрошення.** GET показує загальну форму без деталей події. Для гостя зберігаємо хеш одного очікуваного запрошення у серверній сесії, а після входу чи реєстрації повертаємо на `/invite/continue/` без токена в `next`. Тільки явний POST із CSRF повторно перевіряє чинність за хешем і створює `EventAccess` для поточного акаунта. Після успіху прибираємо очікуване запрошення із сесії й переходимо на звичайну сторінку події. У повторному сеансі вже наданий доступ зберігається за акаунтом.
- **Видача посилання.** Після створення приватної події або зміни видимості автор натискає «Створити запрошення». Сервер генерує криптографічно випадковий токен, а база зберігає тільки хеш. Автор бачить готове посилання один раз після успішної генерації. Якщо посилання втрачено, створює нове. Ротація закриває старий URL, вже надані дозволи акаунтів діють. Сторінки з токеном використовують `Referrer-Policy: no-referrer`. На публічному сервері маршрут із токеном виключається з журналів URL або маскується.
- **Зміна видимості.** Перехід у публічний режим скидає токен і дозволи. При наступному переході в приватний потрібне нове запрошення. Попередні записи та коментарі зберігаються. Учасник без нового дозволу бачить у профілі загальний підпис «Приватна подія» без назви, дати, обкладинки й посилання на сторінку. Він може скасувати власний запис із профілю. Якщо доступ згодом повернувся, картка знову показує подробиці. Скасування не відкриває приватні дані й повертає в профіль, якщо сторінка події недоступна.
- **Видалення.** Видалення події прибирає обкладинку, коментарі, записи та дозволи. Старі сторінка й запрошення повертають 404. Дії, які змінюють стан, виконуються через POST із CSRF.

Компроміси першої версії: для прийняття приватного запрошення потрібен акаунт, а наданий дозвіл діє до зміни видимості або видалення події. Ротація URL керує майбутнім прийняттям запрошень і не відкликає доступ окремого учасника. Email учасників у каталозі, коментарях і списку учасників не показуємо.

## 6. Місця, транзакції та повторні запити

Єдине джерело кількості зайнятих місць — записи `Participation`. Залишок дорівнює `capacity − кількість записів`. Каталог і сторінка можуть показати залишок на момент читання. Рішення про запис завжди приймає сервер за поточним станом.

1. Для SQLite задаємо `transaction_mode=IMMEDIATE`, обмежений `timeout` і короткі явні блоки `transaction.atomic()`. Транзакція для операції починається до читання актуальних прав, часу початку, місткості та записів. `ATOMIC_REQUESTS` вимкнено, шаблони та декодування картинок виконуються поза транзакціями.
2. Запис спочатку перевіряє доступ. Якщо користувач уже записаний, повертаємо той самий стан без другої участі. Інакше перевіряємо час початку та наявність місця й створюємо запис. Другий одночасний запис бачить зміни першого після його завершення. Унікальність пари в базі захищає від дублювання.
3. Скасування видаляє тільки запис поточного користувача і дозволене також після початку. Повторне скасування є безпечною порожньою дією. Автор займає місце лише за власним явним записом.
4. Зміна місткості в транзакції перечитує кількість учасників. Якщо нова місткість менша, форма показує поточний мінімум і вся зміна відкочується. Зміна видимості, видалення, прийняття й ротація запрошення та додавання коментаря також повторно перевіряють необхідні права й стан усередині транзакції.
5. Для підтвердженої тимчасової зайнятості SQLite після тайм-ауту показуємо контрольовану відповідь 503 з можливістю повторити дію. Запис, скасування і прийняття запрошення витримують повторну відправку. Помилки цілісності чи інші помилки бази обробляємо за їхньою причиною.

Ця схема передбачає одну спільну SQLite-базу. Для публічної версії хакатону потрібні один екземпляр застосунку, постійний диск для бази й HTTPS. Якщо згодом потрібні кілька екземплярів або більше одночасних записів, перехід на PostgreSQL включатиме блокування рядка події у всіх операціях, що змінюють її стан або участь, і повторний прогін тестів конкурентності.

Підтвердження механізмів у документації Django: [режими транзакцій SQLite](https://docs.djangoproject.com/en/5.2/ref/databases/#transactions-behavior), [часові пояси у формах](https://docs.djangoproject.com/en/5.2/topics/i18n/timezones/#time-zone-aware-input-in-forms), [пошук у SQLite](https://docs.djangoproject.com/en/5.2/ref/databases/#substring-matching-and-case-sensitivity).

Після першого рев’ю зіставляємо слабкі оцінки зі сценаріями нижче й виправляємо причини за пріоритетом. Час на деплой залежить від того, коли основний сценарій і запуск за README вже перевірені.

### Як підтримувати план під час збірки

Перед кожним підблоком звіряємо його з чинним кодом і залежними підблоками. Наприклад, перед зміною видимості проходимо правила каталогу, обкладинки, запрошень і профілю. Перед зміною місткості звіряємо запис, скасування й список автора. Якщо нове рішення краще узгоджується з вимогами або усуває проблему, замінюємо старе рішення у відповідних розділах цього файлу, оновлюємо сценарії перевірки та продовжуємо за оновленим планом.

Під кожним завершеним підблоком фіксуємо команду або сценарій, фактичний результат і відкриті перевірки.

| Підблок | Перевірка та результат |
| --- | --- |
| Акаунти й налаштування | Міграції застосовано на чистій локальній базі. Перевірено реєстрацію, нормалізацію email, відхилення дубля, вихід та CSRF. |
| Події, каталог і обкладинки | Перевірено створення, редагування, пошук після перейменування, фільтр майбутніх публічних подій, конвертацію картинок і збереження обкладинки після відхиленої правки. |
| Участь, коментарі, профіль і керування | Тести проходять повний сценарій з двома акаунтами. Перевірено права автора, повторні дії, останнє місце, зміну місткості та очищення після видалення. |
| Приватні запрошення й видимість | Перевірено закриту сторінку й обкладинку, прийняття після реєстрації, ротацію, зміну видимості та прихований запис у профілі. |
| Збірка | `python manage.py test` — 15 тестів пройшли. `python manage.py check` — без помилок. `python manage.py makemigrations --check --dry-run` — змін немає. Локальні HTTP-запити до каталогу, реєстрації та CSS повернули 200. У браузері перевірено навігацію до форми реєстрації та порожній результат пошуку. |

Для подій розділяємо предикат видимості й можливість скасувати власний запис. Видимість перевіряємо у запитах бази для сторінок і файлів. Для скасування ідентифікуємо запис за користувачем і повертаємо у профіль, якщо подія для нього прихована; той самий результат отримує запит без власного запису. Це прибирає різницю у відповіді для прихованих і відсутніх подій.

Для запису, редагування й приватності транзакційний сервіс отримує ID події та користувача й перечитує зміни з бази. Форма валідовує введення і готує обкладинку до транзакції, щоб декодування не блокувало інші записи.

Автотести запускаємо на окремій тимчасовій файловій SQLite-базі. Це відтворює блокування між з’єднаннями так, як у звичайному запуску застосунку, і зберігає основну базу проєкту.

## 8. Перевірка рішень і приймання

| Сценарій | Очікуваний результат | Що перевіряє |
| --- | --- | --- |
| Два користувачі одночасно записуються на одне вільне місце | Рівно один запис, другий бачить «Місць немає», залишок 0. Для тесту потрібні два окремі з’єднання з файловою тестовою SQLite-базою. | Перевірка місткості всередині короткої транзакції. |
| Користувач двічі записується або скасовує участь | Один запис після повторного запису, нуль після повторного скасування. Профіль і список автора збігаються. | Унікальність і безпечне повторення дії. |
| Автор одночасно з новим записом зменшує місткість | Фінальна місткість не нижча за кількість учасників. Операція, яка стала недопустимою після першої зміни, показує повідомлення. | Спільне правило транзакцій для запису та редагування. |
| Інший акаунт відкриває права керування публічною подією | Редагування, видалення, генерація запрошення та список учасників недоступні. Дані події не змінюються. | Серверні права автора. |
| Гість та акаунт без дозволу відкривають приватну подію | Каталог, пошук і профіль без участі її не містять. Сторінка, обкладинка та дії закриті. | Узгодженість приватності між усіма маршрутами. |
| Гість приходить за запрошенням і реєструється | Після реєстрації повертається до підтвердження, приймає запрошення й бачить подію. Інший акаунт у тому самому браузері без власного дозволу її не бачить. | Взаємодія запрошення, входу, сесії й дозволу акаунта. |
| Автор створює нове запрошення | Старе посилання недійсне навіть якщо користувач відкрив форму до ротації. Акаунт, який уже прийняв запрошення, зберігає доступ. | Повторна перевірка токена під час POST. |
| Публічна подія з учасниками стає приватною | Учасник бачить лише запис без подробиць і може його скасувати. Після нового запрошення повна картка знову доступна, якщо участь збережена. | Узгодженість профілю й приватності при зміні видимості. |
| Редагування місткості чи обкладинки не проходить валідацію | Початкові поля, обкладинка та участь зберігаються. | Цілісність даних при частковій помилці. |
| Пошук «КИЇВ», прострочена подія, порожній коментар | «Київ» знаходиться. Подія з минулим часом не потрапляє в каталог і новий запис закритий. Порожній коментар відхиляється. | Unicode, часові правила й валідація форм. |
| Автор видаляє подію | Сторінка, обкладинка й запрошення недоступні. Записів і коментарів у базі та карток у профілі немає. | Очищення пов’язаних даних. |

Інтеграційні тести Django підтвердили, що два користувачі не можуть одночасно зайняти останнє місце, повторна відправка не створює дубля, а одночасне зменшення місткості зберігає правило «учасників не більше за місця».

Команда автотестів — `python manage.py test`. README описує встановлення залежностей, налаштування середовища, міграції, локальний запуск і тести. Секрети сесій, дозволені хости, режим debug і шлях бази для деплою задаються через середовище. Локальні секрети та база виключаються з Git. Перед публічним запуском перевіряємо `DEBUG=False`, HTTPS, захищені cookies, ліміт розміру запиту на сервері, обмеження частоти входу та збереження даних після перезапуску.

## 9. Бонуси та готовність до здачі

Після повідомлення «Потрібна ручна перевірка» додаємо окремий старт для ізольованого середовища. Він читає `PORT`, застосовує міграції, обслуговує локальні статичні файли й має `/healthz/`. Режим оцінювання використовує HTTP, перевірку Host та вимкнений DEBUG. Публічний режим надалі вимагає HTTPS і заданий секрет. Dockerfile дає другий спосіб запустити цей самий процес. Повідомлення оцінювача не містить журналів, тому точна причина першої відмови невідома.

Оновлення інтерфейсу змінює шаблони й CSS. Перевіряємо навігацію, форми, видимість приватних подій і мобільну ширину зі збереженням серверних маршрутів.

Захисна перевірка охоплює контроль доступу й CSRF, кешування, екранування тексту, поведінку неавторизованих запитів та розміри завантажень. Для всіх HTML-відповідей додаємо політику ресурсів, сумісну зі статикою з цього самого застосунку. Ліміти розміру запиту застосовує HTTP-сервер режиму оцінювання.

Після оновлення: 18 автотестів пройшли, нових міграцій немає. `start.py` із порожньою SQLite-базою та заданим `PORT` застосував міграції. `/healthz/`, каталог, реєстрація, CSS та нове зображення повернули HTTP 200. Головну сторінку переглянуто в браузері. Окрема перевірка Docker і результат повторної спроби на платформі оцінювання залишаються відкритими.
